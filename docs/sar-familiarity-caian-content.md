## 内容规模与完整性

- ★1、★2、★3 各 10 条一次性常规话题，共 30 条。
- 星级事件 3 条：管理员证、这个答案对我而言很有意义、以前的我也很好。
- Sully 在 SAR 时的一次性特殊遇见 1 条，条件为 `sully-in-sar`。
- 合计 34 场景、229 节点、166 条选项；日常时段 4 条、天气 8 条、星期 21 条，共 33 条。
- 原文 528 条 C/A 台词与实现台词逐句多重集合相等；没有省略分支，也没有让模型改写台词。舞台备注与卡片内容转换为 narrator、effect 和 reward。
- 所有节点可达，无悬空跳转、无循环；所有角色表情引用均来自既有立绘表。★1“再叫一次？”使用明确要求的 `shy`。
- ★4、★5 没有补写内容。

## 选项和流程整理

文档大量使用选项简称作为分支名，实现保留用户看见的完整选项，直接连到对应台词。需要特别说明的错名是：

| 原选项 | 原分支名 | 实现 |
| --- | --- | --- |
| C2-02 玩过 | 提过 | 对应“你也玩过啊！” |
| C2-08 喵 | 不许猫语 | 对应“我还没说！” |
| C2-10 那我走了 | 路过 | 对应“等等啊！” |
| ★2 Zzzzzzz…… | ZZZzzzz | 对应“抱歉，很无聊对吧？” |

C2-02 最末句“如果是你的话，我还挺想知道你玩完会怎么想。”作为三个选项共同收尾。

★1“什么记录？”只有说明而没有明确同意落点，因此在说明后补用已有“好啊 / 不要”选项。拒绝直接进入道别，不生成成员卡。未改写角色台词。

保留原文“想跟别你讲话”等字词，没有擅自润色。★2 拒绝后仍回到正式问题是原剧本走向；阅读器可随时离开并保存断点，提供场景之外的退出能力。

## 演出和纪念物

| 事件 | 数据节点 / effect | 当前实现的行为 |
| --- | --- | --- |
| ★1 管理员证 | photo / admin-card | 凯恩 chibi 作为正式管理员证证件照 |
| ★1 成员登记 | member-card / membership-card，interactive | 用户明确同意后，确认或调整自己的 chibi，生成 SAR 成员 #0001 卡；成员名使用用户当前名称 |
| ★2 会议记录 | meeting-record | 显示会议议题、三位参与者、选择对应的结论和“讨论仍然有意义”备注 |
| ★2 合照 | photo-studio，interactive | 三位 chibi 可移动与缩放、用户可修改自己的 chibi、可加入自己的角色、选择活动室背景；确认拍照后发纪念照片 |
| ★2 照片展示 | photo-reward / notice | 显示日期及照片背面的凯恩字句；照片包含用户角色时，补显示“似乎朋友们也都在！” |
| ★3 旧式卡展示 | spare-card / memory-card | CSS 绘制空白存档卡的展示，此处尚未发放 |
| ★3 获得卡片 | reward / memory-card | 空白存档卡入纪念物，保留略歪的“（User名） / 彼方”标签与完整说明 |

纪念物 ID：`caian-membership`、`caian-meeting`、`caian-photo`、`caian-memory-card`。由共享引擎在首次离开相应奖励节点时原子发放；回放不得重复发物品。

对话默认只有凯恩居中；艾文实际发言时临时双人同框，凯恩再次讲话即回到单人。提及艾文或设置听者情绪不会触发出场；叙述沿用最近说话者，续读与回放相同。凯恩七种表情已在 `public/sar-portraits/Caian` 本地提供，艾文插话使用其六种本地表情；特殊演出保留台词旁的情绪头像。

会议结论存在选项的 `flags.meetingConclusion`，分别为“未得出结论”“肘击系统？（被驳回）”“下次再议”。会议记录文本的 `{{meetingConclusion}}` 由阅读器/奖励存档替换。

照片编辑的日期、位置、缩放、背景、用户形象与加入的角色由交互演出保存；内容文件不伪造照片编辑结果。

自己的仓库「纪念」可查看上述证件、会议记录、合照与存档卡，保留获得当时的姓名和图片，不随之后换形象重拍。「图鉴 → 名册 → 回忆」重看已完成剧情，未完成标题不剧透。完整 ZIP 备份带走照片及其嵌套本地图片引用；纯文字备份保留剧情进度、纪念文字和构图，剥离图片。

## 日常对话

通常组合为“时段 + 天气 + 星期”三句。星期数组按 `Date.getDay()`，0 为周日。当前个人线入口使用世界 seed 与日期确定的彼方模拟天气：clear 对应晴天，rain / storm / snow 归入雨雪类，其余归入阴云类；底层也支持传入明确的天气类别。这不是额外请求真实天气或模型生成的一段说明。
